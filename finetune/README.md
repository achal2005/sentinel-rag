# finetune/ — LoRA router experiment

Fine-tune a small model to perform Sentinel's **routing** classification, and
benchmark it head-to-head against the prompted baseline on `evals/golden.json`.

This satisfies the build plan's evidence rows **"Fine-tuning → training artifact +
benchmark table"** and **"Fine-tuned-router vs. Gemini Flash"**.

## The task

Given a customer request, predict:

| field | values |
|---|---|
| `route` | `answer` \| `action` \| `escalate` \| `spam` |
| `intent` | short snake_case label |
| `urgency` | `low` \| `medium` \| `high` |
| `action_required` | bool |

## Baseline to beat

Prompted `llama3.2:3b` router (`backend/app/router.py`), scored by
`backend/app/eval_routing.py` on the 35 golden cases:

- **Routing accuracy: 88.6%** · urgency 82.9% · escalation recall 81.8% ·
  answerable over-escalation 0% · ~3.0 s/case.

Honest note: this baseline is already strong, so the LoRA router may match rather
than crush it. The point is a real, measured fine-tuning experiment — not a
guaranteed win. Report whatever the data shows.

## Dataset — `data/train.jsonl`, `data/val.jsonl`

Generated by [`make_dataset.py`](./make_dataset.py). Key properties:

- **Disjoint from `evals/golden.json`** (the held-out test set). The generator
  hard-checks every example against golden inputs — no leakage.
- **Labels correct by construction:** each template belongs to a route bucket, so
  slot-filling can't flip the label.
- **Balanced** across routes (~40/25/25/10 answer/action/escalate/spam) so the
  model actually learns minority classes.
- **Variety via filtered paraphrasing:** an optional `--paraphrase` pass rewords
  requests with `llama3.2:3b`. A guard rejects any paraphrase that drifts into
  support-agent voice (the model's failure mode) and falls back to the clean
  template — the dataset never gets corrupted.

```bash
python finetune/make_dataset.py --n 400 --paraphrase
```

Each row:

```json
{"text": "How do I roll back a deployment?", "route": "answer",
 "intent": "how_to", "urgency": "low", "action_required": false}
```

## Plan

1. `make_dataset.py` → `data/{train,val}.jsonl` (400 ex, balanced, leakage-checked)  ✅
2. Kaggle T4: `kaggle_train.py` — Llama-3.2-1B + PEFT LoRA → adapter + benchmark  ✅
3. Benchmark recorded (see Results)  ✅

## Results (2026-08-15, unsloth/Llama-3.2-1B-Instruct, LoRA r=16, 3 epochs, T4)

| Metric | Prompted baseline (llama3.2:3b) | LoRA router (fine-tuned 1B) |
|---|---|---|
| **Routing accuracy** | **88.6%** (31/35) | **85.7%** (30/35) |
| Urgency accuracy | 82.9% | 68.6% |
| Escalation recall | 81.8% | 63.6% |
| Answerable over-escalation | 0% | 0% |
| Trainable params | — | 3.41M (0.28% of 1.24B) |

**Delta: −2.9 pts routing. The fine-tune did not beat the prompted baseline** — an
honest, expected outcome given a strong baseline, a 1B base, and ~340 synthetic
training examples. The experiment's value is the reproducible methodology (no
train/test leakage, identical eval harness) and the demonstrated PEFT/LoRA skill,
not a headline win. Plausible ways to close the gap: more/richer training data,
a stronger base (Qwen2.5-1.5B), more epochs, or class-weighting for urgency and
escalation (its weakest metrics). Reporting the negative result honestly is the
point.

Training runs on a **free cloud GPU** (Kaggle T4); the local AMD GPU can't train it.

## How to run step 2 on Kaggle

1. **Create a Kaggle Dataset** named `sentinel-router` containing three files:
   `finetune/data/train.jsonl`, `finetune/data/val.jsonl`, `evals/golden.json`.
   (They'll appear at `/kaggle/input/sentinel-router/`.)
2. **New Notebook** → Settings → Accelerator = **GPU T4 x1**; attach the dataset.
3. **Hugging Face token** (for the gated Llama base): accept the license at
   huggingface.co/meta-llama/Llama-3.2-1B-Instruct, then Add-ons → Secrets →
   add `HF_TOKEN`. *Or* skip this and edit `BASE` in `kaggle_train.py` to the
   ungated `unsloth/Llama-3.2-1B-Instruct`.
4. Paste `kaggle_train.py` into a cell and run. It trains (~a few min on T4),
   saves the adapter to `/kaggle/working/sentinel-router-lora`, and prints the
   **benchmark table vs. the 88.6% baseline**.
5. Download the adapter (Output tab) if you want to convert it to GGUF and serve
   it locally in Ollama later.

The eval inside the notebook uses the **same metric definitions** as
`backend/app/eval_routing.py`, so the comparison is apples-to-apples.
